# Время хранится в UTC, показывается в поясе зрителя

**Status**: accepted

**Дата**: 12 ноября 2026

## Context

Сервис работает по календарю одного владельца: зона `Europe/Moscow`, рабочие дни
понедельник–пятница. Гость может находиться в другом часовом поясе. README
фиксировал рабочие часы 10:00–18:00, но в задании встречается 09:00–18:00;
источники расходятся. Также нужно было выбрать, хранить время как UTC-момент
или как локальную строку Москвы, и решить, показывать ли гостю его пояс.

## Decision

- Рабочие часы: **09:00–18:00**, понедельник–пятница, без праздников, отпусков
  и обеденных перерывов. Рабочий день заканчивается в 18:00: встреча должна
  закончиться не позже.
- Часовой пояс владельца — IANA `Europe/Moscow`. Смещение постоянно +03:00,
  перехода на летнее/зимнее время нет; переходы не обрабатываем.
- Внутри сервиса и в API время — абсолютные моменты UTC (`utcDateTime`,
  ISO 8601 с `Z`). Локальное московское время вычисляется для правил
  доступности и отображения.
- «Сегодня», день недели и границы рабочего дня считаются по московскому
  календарю и серверным часам; клиент не присылает текущее время.
- Гость видит время в своём поясе: зона определяется через `Intl` с
  возможностью выбрать другую вручную. API пояс гостя не принимает и не хранит.
  Владелец всегда видит московское время.

## Consequences

- Сравнение броней, проверка пересечений и окно записи не зависят от формата
  отображения: везде сравниваются UTC-моменты.
- Фронтенд отвечает за конвертацию и подпись пояса. Ошибка или отсутствие зоны
  в браузере отображается как `Europe/Moscow`.
- Дни в календаре гостя группируются по московской дате; местное время — только
  формат показа. Иначе «14 дней» и рабочие дни означали бы разное для разных
  гостей.
- Правило 09:00–18:00 продублировано в README и на главной странице; при
  изменении его нужно править в обоих местах.
- Тесты границ (09:00, 18:00, выходные, смена даты при конвертации) становятся
  обязательными; браузерный сценарий задаёт пояс через `timezoneId`.

## Alternatives

- **Хранить локальные строки Москвы**: проще читать, но сравнение моментов и
  показ гостю в другом поясе требуют ручной арифметики и легко ломаются.
- **Фиксированное смещение `+03:00` без IANA-имени**: короче, но теряет
  читаемое имя зоны и корректность, если правила зоны когда-нибудь изменятся.
- **Конвертировать время на сервере по поясу гостя**: API пришлось бы принимать
  и валидировать пояс в каждом запросе, а кэширование ответов усложнилось бы.
- **Показывать гостю только Москву**: меньше UI, но гость из другого пояса
  вынужден пересчитывать время вручную.
