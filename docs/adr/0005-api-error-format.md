# Формат ошибок API: конверт с машинным кодом

**Status**: accepted

**Дата**: 12 ноября 2026

## Context

API потребляют сгенерированный TypeScript SDK и интерфейс. UI должен различать
случаи (занятый слот, неотменяемая бронь, ошибка валидации) без разбора текста,
а человек — видеть понятное сообщение. Нужен стабильный контракт ошибок,
который не придётся ломать при добавлении новых случаев.

## Decision

Ошибка всегда имеет вид:

```json
{ "error": { "code": "SLOT_TAKEN", "message": "Это время уже занято", "details": [...] } }
```

- `code` — стабильный `SCREAMING_SNAKE_CASE`, по нему принимает решения UI;
- `message` — человекочитаемый текст на русском, его можно показать как есть;
- `details` — опционален, для валидации это массив `{ field, message }`.

Коды и статусы:

| Код                       | Статус | Когда                                      |
| ------------------------- | ------ | ------------------------------------------ |
| `VALIDATION_ERROR`        | 400    | неверные поля или query-параметры          |
| `MEETING_TYPE_NOT_FOUND`  | 404    | нет типа встречи                           |
| `BOOKING_NOT_FOUND`       | 404    | нет брони                                  |
| `SLOT_TAKEN`              | 409    | пересечение при создании брони             |
| `BOOKING_NOT_CANCELLABLE` | 409    | бронь уже отменена или `end <= now`        |
| `NOT_FOUND`               | 404    | неизвестный маршрут                        |
| `INTERNAL_ERROR`          | 500    | непредвиденная ошибка, без стека и деталей |

Глобальный обработчик Fastify приводит к этому формату и собственные ошибки
маршрутизации, чтобы клиент не получал два разных формата.

## Consequences

- UI переключается по `code`, а `message` показывает как запасной вариант;
  русский текст живёт на сервере, отдельная локализация не нужна.
- Новые коды добавляются аддитивно; существующие коды и их статусы не меняются.
- SDK получает тип `ErrorResponse` и перечисление кодов; тесты проверяют код,
  статус и наличие `details` для валидации.
- Внутренние ошибки не раскрывают стек и текст исключения.

## Alternatives

- **RFC 9457 `application/problem+json`**: стандарт, но его поля (`type`,
  `title`, `detail`, `instance`) избыточны для одного клиента и хуже ложатся
  на решение по коду.
- **Только строки сообщений**: UI пришлось бы сравнивать текст, что ломается
  при любой правке формулировки.
- **Отдельный код на каждое поле валидации**: раздувает перечисление; массив
  `details` покрывает то же самое.
