# Главная страница — маркетинговая, а не страница владельца со списком встреч

**Status**: accepted

## Context

Сервису нужна главная страница, которая рассказывает о нём и ведёт на страницу
записи; на этом этапе страница записи может быть заглушкой. В Cal.com гостевая
точка входа устроена иначе: страница владельца (`cal.com/<username>`)
со списком типов встреч, а маркетинговая главная живёт отдельно на `cal.com`.

## Decision

Главной страницей считаем маркетинговую страницу о сервисе: она описывает, как
устроено бронирование, и ведёт на `/book`. Страница владельца со списком
типов встреч появится отдельно на этапе бронирования, когда в контракте будут
типы встреч.

## Consequences

- Главная страница статична: она не обращается к API и не показывает типы
  встреч, поэтому её можно сделать до появления контракта бронирования.
- Факты о сервисе — правила записи и шаги — дублируются в разметке. При
  изменении правил их придётся править и в README, и на странице.
- `/book` сейчас заглушка, но требование «главная ведёт на страницу записи»
  проверяется тестом уже на этом этапе.
- Страница владельца со списком типов встреч и кабинет владельца остаются вне
  этого этапа.

## Alternatives

- **Страница владельца как главная** (`cal.com/<username>`): ближе к
  Cal.com, но требует API типов встреч и данных владельца, то есть тянет часть
  следующего этапа.
- **Кабинет владельца как главная** (`cal.com` → `/links`): это инструмент
  владельца, а не точка входа гостя.
