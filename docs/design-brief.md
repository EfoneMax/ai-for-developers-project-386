# Шаг «Проектирование бронирования»: brief и план

**Статус:** подготовка
**Проект:** «Календарь звонков», `EfoneMax/ai-for-developers-project-386`
**Трекер:** GitHub Issues, работа через `gh` CLI
**Дата:** 11 ноября 2026 г.

## Brief

### Цель шага

Спроектировать бронирование до реализации: закрыть решения по ролям, модели
встреч и броней, правилам времени, API, интерфейсу и тестированию. Код
бронирования на этом шаге не пишем.

### Пункт назначения карты

> Согласованная спецификация сервиса «Календарь звонков», по которой можно
> нарезать вертикальные тикеты и начать реализацию без новых функциональных
> решений: роли, модель встреч и броней, правила времени, API, интерфейс и
> границы тестирования.

### Что уже есть

- `api/main.tsp` — только `GET /api/health`.
- `server/src/app.ts` — только health-маршрут.
- `web/src/pages/BookingPage.tsx` — заглушка `/book`.
- Vitest: дымовой тест сервера и тесты лендинга.
- `README.md` уже содержит часть правил записи.
- `GLOSSARY.md` и ADR: главная страница маркетинговая, роутинг через
  `react-router-dom`.
- `gh` авторизован (`EfoneMax`), версия `2.103.3`; native sub-issues и
  `blocked-by` доступны. Метки `wayfinder:*` созданы.

### Уже зафиксированные решения, которые нужно подтвердить

Из `README.md`:

- часовой пояс владельца — `Europe/Moscow` (UTC+3);
- рабочие дни — понедельник–пятница, 10:00–18:00;
- шаг доступных стартов — 30 минут;
- окно записи — 14 календарных дней, начиная с сегодняшнего;
- длительность слота равна длительности выбранного типа встречи;
- пересечения запрещены, включая частичные и между разными типами встреч;
- встречи встык разрешены;
- одновременные запросы на один слот обрабатываются атомарно.

Эти правила нужно подтвердить на карте или осознанно изменить. Если решение
меняется, его нужно записать в тикете и, при необходимости, в ADR.

### Открытые вопросы

- Точные рабочие часы: README говорит 10:00–18:00, в задании есть пример
  09:00–18:00.
- Начинается окно записи с сегодняшнего дня или с завтрашнего.
- Какие поля обязательны у типа встречи и брони.
- Можно ли редактировать и удалять типы встреч.
- Как хранить тип встречи в брони: ссылку или снимок полей.
- Формат API-ошибок и код ответа при конфликте.
- Нужна ли идемпотентность при повторной отправке формы.
- Какие страницы и состояния есть у гостя и владельца.
- Какой браузерный раннер использовать: в репозитории его пока нет.
- Что входит в общую команду проверок, а что запускается отдельно.
- Какая небольшая функция станет первым вертикальным срезом.
- Как настроить release-please после первой функции.

### Границы шага

- Не менять `api/main.tsp` и не запускать генерацию SDK.
- Не писать код бронирования.
- Не создавать implementation-тикеты до согласования спецификации.
- Не смешивать decision-тикеты карты с тикетами реализации.
- Не добавлять `ready-for-agent` к тикетам карты.

### Следующая сессия

Начать отдельную сессию и вызвать `/wayfinder`. В сессии должны быть доступны
этот brief, `AGENTS.md`, `README.md`, `GLOSSARY.md`, ADR и конфигурация
трекера.

## План по сессиям

### Сессия 0. Подготовка

- [ ] Выполнить `gh auth login`, проверить `gh auth status`.
- [ ] Проверить версию `gh`. Если меньше `2.94` — обновить или выбрать fallback
      из `docs/agents/issue-tracker.md`.
- [ ] Проверить/создать метки `wayfinder:map`, `wayfinder:research`,
      `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`.
- [ ] Убедиться, что доступны проектные `/wayfinder`, `/to-spec`,
      `/to-tickets`.
- [ ] Прочитать `AGENTS.md`, `README.md`, `GLOSSARY.md`, ADR, `api/main.tsp`,
      текущие тесты.
- [ ] Выписать отдельно уже принятые решения, чтобы не проектировать их заново.
- [ ] Выписать открытые вопросы, но не решать их до карты.
- [ ] Проверить, что рабочее дерево чистое.

**Результат:** авторизованный трекер, метки и список предрешений.

### Сессия 1. Карта решений через `/wayfinder`

- [ ] Запустить `/wayfinder` в отдельной сессии.
- [ ] Сформулировать пункт назначения своими словами.
- [ ] Пройти grilling в ширину: роли, доменная модель, время, конфликты, API,
      UI, тесты, поставка.
- [ ] Создать map-issue с меткой `wayfinder:map` и секциями `Destination`,
      `Notes`, `Decisions so far`, `Not yet specified`, `Out of scope`.
- [ ] Создать дочерние decision-тикеты с метками `wayfinder:<type>`.
- [ ] Вторым проходом связать тикеты зависимостями.
- [ ] Запустить research-субагентов для research-тикетов, если они нужны.
- [ ] Остановиться после создания карты: решения в этой сессии не принимаются.

**Результат:** карта и дочерние вопросы с зависимостями.

#### Ориентировочные блоки вопросов

| Блок              | Что решить                                                                    |

### Сессии 2–N. Проход по карте

На каждой сессии:

- [ ] Загрузить карту.
- [ ] Взять первый доступный незанятый тикет.
- [ ] Назначить тикет на себя — это claim.
- [ ] Определить тип по метке: `research`, `prototype`, `grilling`, `task`.
- [ ] Для grilling использовать `grilling` и `domain-modeling`.
- [ ] Записать решение комментарием: решение, почему, следствия для API/UI/тестов,
      что осталось неясным, новые тикеты.
- [ ] Закрыть тикет.
- [ ] Добавить gist в `Decisions so far` карты.
- [ ] Выпустить новый «туман» в тикеты, если он стал формулируемым.
- [ ] Вынести в `Out of scope` то, что оказалось вне пункта назначения.
- [ ] Остановиться после одного тикета; research-тикеты можно вести параллельно.

**Ориентировочный порядок:**

1. Роли и границы продукта.
2. Модель типа встречи.
3. Модель брони.
4. Часовой пояс и рабочие часы.
5. Окно записи и генерация слотов.
6. Пересечения, встык и атомарность.
7. API-контракт и ошибки.
8. Гостевой интерфейс.
9. Кабинет владельца.
10. Границы и инструменты тестирования.
11. Первый вертикальный срез и контрактная цепочка.
12. Общая команда проверок и release-please.

Порядок может измениться из-за зависимостей. Не решать API раньше правил
времени и конфликтов.

**Ожидаемая длительность:** 4–6 сессий по одному тикету.

### Сессия N+1. Спецификация через `/to-spec`

- [ ] Начать отдельную сессию.
- [ ] Загрузить карту и все закрытые дочерние тикеты с комментариями.
- [ ] Согласовать с пользователем границы тестирования.
- [ ] Запустить `/to-spec`; скилл не должен интервьюировать.
- [ ] Проверить спецификацию по чек-листу.
- [ ] При пробеле вернуться в карту, создать тикет, закрыть его и обновить
      спецификацию.
- [ ] Опубликовать спецификацию в трекер с меткой `ready-for-agent`.

#### Чек-лист спецификации

- [ ] Роли владельца и гостя.
- [ ] Один заранее заданный владелец, без регистрации и авторизации.
- [ ] Типы встреч: поля, создание, просмотр.
- [ ] Окно записи 14 дней и правило его начала.
- [ ] Рабочие часы и дни.
- [ ] Часовой пояс.
- [ ] Длительность слота равна длительности типа встречи.
- [ ] Шаг доступных стартов.
- [ ] Правило примыкания встреч.
- [ ] Запрет пересечений, включая разные типы встреч.
- [ ] Поведение при одновременных запросах.
- [ ] API: пути, методы, поля запросов и ответов.
- [ ] Создание бронирования.
- [ ] Ошибки валидации.
- [ ] Конфликт занятого времени: код ответа и понятное сообщение.
- [ ] Границы тестирования: прямые запросы к API и браузерный сценарий с
      настоящим сервером.
- [ ] Решения по тестированию: модули, швы, что считается хорошим тестом.
- [ ] Out of scope.
- [ ] В спецификации нет конкретных файлов и кода, которые быстро устареют.

### Сессия N+2. Тикеты через `/to-tickets`

- [ ] Запустить `/to-tickets` на основе спецификации.
- [ ] Проверить, что каждый тикет — вертикальный срез через контракт, сервер,
      интерфейс и тесты.
- [ ] Проверить, что каждый тикет демонстрируем или проверяем отдельно.
- [ ] Проверить размер: один тикет помещается в свежий контекст.
- [ ] Проверить зависимости: каждый тикет блокируется только тем, что его
      действительно gate-ит.
- [ ] Пройти quiz от скилла: granularity, blockers, merge/split.
- [ ] Опубликовать тикеты в порядке зависимостей.
- [ ] Применить native blocked-by или fallback `Blocked by: #...`.
- [ ] Поставить `ready-for-agent` на тикеты реализации.
- [ ] Связать каждый тикет со спецификацией.

#### Первый тикет

Первый тикет должен быть небольшим, но полным сквозным срезом. Например:

> Список типов встреч: TypeSpec-модель и маршрут → OpenAPI → сгенерированный
> SDK → Fastify-маршрут → отображение на странице → API-тест и UI-тест.

В тикете указать:

- [ ] Команды генерации контракта и SDK.
- [ ] Проверку ответа API.
- [ ] Проверку, что сгенерированные файлы не расходятся.
- [ ] Запуск общей команды проверок.
- [ ] Критерии приёмки.

Код этой цепочки появится только на следующем шаге. Сейчас тикет должен быть
постановкой, а не реализацией.

#### Что обязательно должно быть в графе

- [ ] Общая команда проверок, например `mise run check`.
- [ ] API-тесты прямыми запросами.
- [ ] Браузерный сценарий с настоящим сервером.
- [ ] Проверка одного теста с временно нарушенным правилом бронирования:
      сломать правило пересечения, убедиться, что тест падает, вернуть правило.
- [ ] Настройка release-please после первой работающей функции.

### Сессия N+3. Передача в реализацию

- [ ] Проверить, что карта закрыта: все вопросы имеют ответы.
- [ ] Проверить, что спецификация опубликована и не содержит пробелов.
- [ ] Проверить, что у каждого тикета есть зависимости и критерии приёмки.
- [ ] Проверить, что первый тикет не заблокирован.
- [ ] При необходимости обновить `GLOSSARY.md` и ADR.
- [ ] Если менялись файлы репозитория — запустить `mise run check`.
- [ ] Отправить шаг в Хекслете.
- [ ] Следующий шаг начать с `/implement-spec`.

## Финальный чек-лист готовности

- [ ] Карта решений создана и все её вопросы закрыты с записанными ответами.
- [ ] В спецификации есть владелец и гость, типы встреч, окно 14 дней, рабочие
      часы, часовой пояс, длительности, шаг стартов, примыкание и конфликты.
- [ ] Спецификация задаёт API и ожидаемые ответы: создание брони, ошибки данных,
      конфликт занятого времени.
- [ ] Названы границы тестирования, включая прямые API-запросы и браузерный
      сценарий с настоящим сервером.
- [ ] В трекере есть тикеты с зависимостями и ссылками на спецификацию.
- [ ] Первый тикет проводит небольшую функцию через контракт, генерацию, сервер,
      интерфейс и тесты.
- [ ] В графе есть общая команда проверок, API-тесты, браузерный сценарий,
      проверка сломанного правила бронирования и release-please.
- [ ] Можно начинать `/implement-spec` без новых функциональных ограничений.

## Риски и места, где легко ошибиться

- **Часовой пояс и границы 14 дней.** Определить, входит ли текущий день, что
  происходит на границе 14-го дня и как считать слоты на краю рабочего дня.
- **Шаг и длительность.** Старт каждые 30 минут, но слот может длиться дольше.
  Нужно определить допустимые старты и последний старт.
- **Пересечения между разными типами встреч.** Это отдельное правило, его нельзя
  свести к проверке внутри одного типа.
- **Одновременные запросы.** В памяти процесса легко получить гонку между
  проверкой занятости и записью. Зафиксировать атомарную операцию и проверить
  тестом.
- **Формат ошибки конфликта.** UI должен показать понятное сообщение, поэтому
  нужен стабильный код ошибки, а не только текст.
- **Браузерные тесты.** Решить, входят ли они в `mise run check` или запускаются
  отдельной командой, чтобы проверки не стали медленными и нестабильными.
- **Версия `gh`.** Без обновления или fallback можно потерять native sub-issues и
  blocked-by.
- **Контекст для `/to-spec`.** Решения должны быть краткими и самодостаточными,
  иначе карта и все тикеты не поместятся в одну сессию.
- **Смешение типов тикетов.** Карта содержит decision-тикеты, реализация —
  вертикальные slices. Не добавлять `ready-for-agent` к тикетам карты.
- **README уже содержит решения.** Их нужно согласовать, а не дублировать в
  спецификации с другими формулировками.
